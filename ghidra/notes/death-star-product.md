# Death Star as a Shipyard Product

Sides are the game's: 1 Alliance, 2 Empire. Confidence tags: **code read**, **inference** (code read plus a stated assumption), **needs VM**. `hyp:` marks anything not traced through code. The Death Star is CAPSHPSD record 136 (family `0x18`); every rule below keys on the family byte, so each applies to every capital ship (`0x14`..`0x17`) unless a range test says otherwise. Companion notes: `death-star-strategic.md`, `build-delivery.md`, `production-destination.md`, `ai-production.md`, `ai-mission-planning.md`.

## 1. Placement (order to completion)

**The ship exists from the moment of the order.** The build command (`0x211`, order class vtable `0x006611a0`; command object `FUN_0057f230`, vtable `0x00669ad0`) validates through `FUN_005385f0` (order) and `FUN_0057f540` (command), and executes through `FUN_0057f890`, which calls the production facility's slot `+0x1f0` = `FUN_00529ab0` (vtable `0x0065fbf8`, slot 124). That runs `FUN_0052a140`, which for each queued request (container key at entry `+0x18`, class key at `+0x1c`) calls `FUN_004f7d50(container, class, side, ctx, created=1, completed=0)`: the class factory builds the ship object, reparents it into the container (slot `+0xa8`), and sets created (`+0x50` bit 1) with completed (bit 2) clear. `FUN_004f7070` then stores the facility's key at the ship's `+0x38`. The same function's sibling `FUN_0052a2c0` runs the facility's request slot `+0xac(0x16)` per queue entry.

**The container is the destination system's spare fleet, never the system and never an existing fleet.** `FUN_005385f0` builds the route with `FUN_00551190` (side, order kind at route `+0x1c`, mode 3 at `+0x20`), and `FUN_00551a20` → `FUN_00552300` resolves the destination. For a system destination (`0x90..0x97`) `FUN_00552300` asks `FUN_005097d0` for the side's bit-1 spare fleet (`+0x58` bit 1, not destroyed; `FUN_00509b40` asks bit 2, used only when the route kind is `0x270`, Create Fleet). The leg is the better of two room results (`FUN_00552b10`, comparator `FUN_0054fbb0`, "no refusal beats a refusal, then more room"): the system itself refuses ships, the fleet accepts them (`FUN_004fe160`: range inside `[0x14,0x1c]` allowed), so the fleet wins and its key goes out through `param_6` into the request entry (`FUN_0053e020`, entry `FUN_00585420`). The system at order time is the build's destination: the facility's own system by default, or the Destination order's target (`0x214`, `production-destination.md`). Spare maintenance: `FUN_0050be00` drops bit 2 from a spare that holds anything or is destroyed, `FUN_0050bc60` drops bit 1 only from a destroyed one, and `FUN_00512d00` creates a replacement for a side left without one (`fleet-join-split.md`). Confidence: code read for the container, inference for "better of two" selecting the fleet (the system candidate's refusal is the `FUN_00507750` pattern).

**The spare becomes a real fleet on the order day.** `FUN_004f7d50` reparents the new ship into the spare (slot `+0xa8`, `FUN_004f7d50.c:31`) before it sets created (`:37`). The existing-bit hook raises event `0x300` (`FUN_004f2bb0` → `FUN_004fb810` → `FUN_0053f9c0`). `FUN_0053ff90` stores the object at event `+0x3c`, its container at `+0x40` (`FUN_00540450`: object `+0x1c`) and its location at `+0x44`, and the fire slot `FUN_0057a730` calls `FUN_005140c0(object, container, location)`. For the new ship, `FUN_005140c0`:

- calls the container's slot `+0xc4` (`FUN_005140c0.c:104`). For a fleet that is `FUN_004fe870` → `FUN_004fe630`, which counts the fleet's ships in mode 3 (`FUN_00502e30`, created and not destroyed). With one present it sets `+0x58` bit 0 (`FUN_004fe230`), created and completed on the fleet (`FUN_004fe630.c:33-38`). With none left and bit 0 set, it calls slot `+0xac(0x14)` instead and the fleet disbands (`FUN_004fe630.c:21-28`);
- calls `FUN_00529cf0` on the manager named by `+0x38` when the object is not completed (`FUN_005140c0.c:66-77`), which enters the product in the manager's list (section 7);
- numbers it (`FUN_005140c0.c:127` → `FUN_00517760`, `fleet-names.md`).

The spare's own created bit raises a second event `0x300`, whose `FUN_005140c0` calls the system's slot `+0xc4`, `FUN_00508440`. Its fleet branch runs `FUN_0050bc60` and `FUN_0050be00` (`FUN_00508440.c:73-97`): the spare, which now holds a ship, keeps bit 1 (`FUN_0050bc60` drops it only from a destroyed fleet) and loses bit 2, and `FUN_00512d00` makes the side a new bit-2 spare. The same pass numbers the fleet "Fleet N". A spare made by `FUN_00512d00` starts with created and completed clear (`FUN_00512d00.c:16-17`: `FUN_004f7d50(system, 0x8000004, side, ctx, 0, 0)`), so until its first ship it is not existing and every mode-3 walk skips it (`FUN_004ffe70`, hence `FUN_00507ab0`'s count). The route-1 Empire game (`agent_docs/original-save-editing.md`, "Route 1 in the original") shows the result. In its day-115 save, the order day at progress 0, the unfinished Death Star `0x18000df5` "Death Star 1" (`+0x50` `0x42`) sits in fleet `0x8000aea` "Fleet 6" at Coruscant (`+0x50` `0x10046`). The day-123 save holds the same, and at completion both read `0x30147` under the same keys and names. So the mode-3 count of section 2 sees an unfinished Death Star from its order day. A second order refused at that system on the order day has not been observed separately: at the time of the VM try, a maintenance shortfall made every class invalid (`manufacturing-build-selection.md`). Confidence: code read; save evidence for the result.

**Completion** (`FUN_0052b960` → `FUN_0052bee0`): the ship's `+0x50` gets deployed (bit 16), then en route active (bit 5) only when the facility's location key and the ship's differ, then completed (bit 2). A build at the yard's own system never travels: the finished Death Star is a member of the fleet it was created in, which is the VM's new Fleet 6 at Coruscant. A Destination elsewhere sets the ship (not the fleet) en route; arrival is galaxy event `0x387` (`build-delivery.md`). Confidence: code read.

**Rule for every capital ship, both sides:** at order time a new object in the container its leg chose, and completed in place at completion. The container is the destination system's bit-1 spare fleet, or a destination fleet itself:

- **One Build shares one fleet.** `FUN_005385f0.c:200-219` resolves every unit of a Build in one validation pass through `FUN_00551a20` → `FUN_00552300` → `FUN_005097d0`, a pure query (the side's first undestroyed fleet with `+0x58` bit 1, walked in mode 4). It appends each (container, class) pair to the command's list (`FUN_0053e020`). `FUN_0057f890` hands that list to `FUN_00529ab0` → `FUN_0052a140`, which creates each unit in its entry's container (entry `+0x18`). The events the creation raises are queued, so every unit of one Build lands in one fleet.
- **A Build at a busy yard.** It first destroys whatever its manager was building: `FUN_00529ab0` is `FUN_0052a2c0`, then `FUN_0052a140`.
- **Later Builds and Moves into the same system.** The bit-1 spare keeps its bit while it holds ships (`FUN_0050bc60.c:41-51` drops it only from a destroyed fleet), so every later Build bound for the system, and every ship moved there, lands in the same fleet until that fleet is destroyed or disbands (code read; in the route-1 Empire game played on, a ship moved to Averam joined the fleet an earlier move had made there).
- **A fleet destination.** The Build's destination is its manager's `+0x7c` (`FUN_004c27b0`, read by `FUN_005385f0.c:204-208`). The Destination order writes `+0x7c` (`production-destination.md`) and may name a fleet for the ship manager. For a fleet, `FUN_00552300` offers the fleet itself, which accepts the range `[0x14,0x1c]` (`FUN_004fe160`), and its usable ships (mode 1, `FUN_00552300.c:100-118`), whose room holds only `[0x1c,0x20)` and `[0x10,0x14)` (`FUN_00500b40`). So a capital ship ordered with a fleet destination is created as an unfinished member of that existing fleet.

Later joining is the ordinary Join or Move.

## 2. The one-per-system room

`FUN_00507ab0` is the system's slot `+0x80` (vtable `0x0065e640`, slot 32; also `0x00663698`, `0x00664098`). It answers one request category at a time: the category range comes from `FUN_0054f5b0(i)` (nine ranges; index 1 is `[0x18,0x1c)`), and the function acts only when the range lies inside `[0x18,0x1c]`. Its outputs: `*p3=1`, `*p4=0`, room `*p5 = FUN_0040f340() - count`, with `FUN_0040f340` returning the literal 1, and the stored status `{0x90, 3}` written beside it.

**What is counted** (code read): `FUN_004ffe70(system, mode)` walks the system's fleets (types `8..0x10`) and `FUN_005003d0(fleet, mode)` their children `[0x18,0x1c)`, with `mode = 3` (`FUN_00550700` passes route `+0x20`, which `FUN_005385f0` sets to 3). Mode 3 accepts `+0x50` bit 6 (existing = created and not destroyed, `object-state-flags.md`). So the count includes: completed Death Stars, uncompleted products already created (the order-time ship, once its fleet passes mode 3), ships of both sides (the iterator's side filter at `+0x14` is 0), ships of fleets that are en route. A moving fleet's container changes at its order (`move-order.md`), so a fleet bound for the system counts there and one ordered away counts at its destination; the port's count is `movement::death_stars_counted_at`, which Build, the Destination order and Move share. It excludes: destroyed ships; a fleet that is not itself existing (an untouched spare, see §1's open point). Confidence: code read for the walk and filter.

**What a Build gives back** (code read, Wine): before its units' legs, `FUN_005385f0` runs `FUN_00552210` for each producer. That lists the ordering manager's products (`FUN_005287f0`) and, through `FUN_00552150` → `FUN_00552000`, runs `FUN_00552dd0(route, request, 0, container)` for each: the product's request goes back into its container and that container's system, since `FUN_0054fca0` adds the request when its last argument is 0 and subtracts it when 1 (`FUN_00551a20` passes 1). The Build replaces those products (`FUN_00529ab0`: `FUN_0052a2c0`, then `FUN_0052a140`), so the Death Star the ordering yard is building leaves the room, and any other one at the destination still fills it. That includes one another yard has queued for the destination: its manager is not the ordering one, so nothing gives it back, and the Build refuses `{0x90, 3}` (settled by this trace). The ds-b line played to day 151 with its Empire maintenance raised by 4000 (`agent_docs/original-save-editing.md`) shows it ("Play evidence", Build over a queued Death Star).

**Where it binds** (code read): `FUN_00552dd0` takes the container found by `FUN_005530d0`, then `FUN_00550eb0` checks the request against the container's arrays and `FUN_00550fb0` against the container's parent (the system) second array (`+0x128`), through `FUN_00550bd0` (nine categories, combiner `FUN_0054fd90` over `FUN_0054fca0`: room minus request, negative room fails and copies the stored status). Request `+1` for category 1 is added by `FUN_005504d0` (family byte of the product) at Build, and by the move leg builders for a moving fleet's Death Star. The Destination order's new legs bind the same way (`FUN_00537180.c:336` → `FUN_00551900` → `FUN_00552dd0(.., 1, ..)`), after `FUN_00552210` gives back the manager's products (`:321`). So: Build (`FUN_00551a20`), Move into a system holding one (`FUN_00551630`), and the retreat candidate test (`FUN_005571c0` → `FUN_00551630`) refuse when room 1 − count minus the request goes negative, i.e. one existing family-`0x18` ship at the destination blocks a second.

**Refusal text.** `{0x90, 3}` has no text. The advisor agent (`FUN_004c2940` Alliance, `FUN_004c0870` Empire) dispatches on the first word: Empire `FUN_004c1550` maps `{0x90,3}` to table slot `+0x2c` (index 11 of `IMP22ACT.SPT`, a droid reaction with a 10-step window); Alliance `FUN_004c3750` handles `{0x90,1}`, `{0x90,2}`, `{0x90,4}` and drops `{0x90,3}` to the generic reaction (`FUN_004c4390`, one of two generic slots). The clip played by Empire slot 11 is not decoded (audit P34). Confidence: code read for the dispatch, **needs VM** for what plays.

## 3. The player's maintenance refusal `{0xf3, 1}`

Two sites, both strict (refuse when need exceeds spare; equality passes), spare = side `+0x58` − side `+0x5c` where side = `FUN_00506ea0(side)` (`DAT_006b2bb0 + 0xc4/0xc8`): capacity `+0x58` = min(mine capacity, refinery capacity) = 50 per pair (`top-bar-resource-counters.md`), `+0x5c` = the smaller allocated half of the load spread by `FUN_0052f6b0`/`FUN_0052f8f0` (inference: it equals the load `+0x74` unless a facility clamps).

1. `FUN_0052e970(side, classKey, quantity, status)`, called by `FUN_005385f0`: for a product family in `[0x10,0x40)` (ships, fighters, troops, facilities), `need = class +0x4c (FUN_0053b870) * quantity`; writes `{0xf3,1}` when `need != 0 && spare < need`. It returns true either way; the order then stops on the non-`-1` status word.
2. `FUN_0057f540` (the command's validate slot): sums `FUN_0053b870` over every queued entry in the command, then writes `{0xf3,1}` when `spare < sum`.

Class maintenance 0 (mines, refineries, characters) never fires it. The Death Star (maintenance 600) needs 600 spare, which is twelve idle mine/refinery pairs. Maintenance counts existing objects, queued products included, so an ordered Death Star consumes the 600 at once and only once. In play (below), a Stop of the queued Death Star raised the Empire's maintenance counter from 309 to 909. Advisor: `{0xf3,1}` is table slot `+0x28` (index 10) on both sides (`FUN_004c1980`, `FUN_004c3b40`). Confidence: code read.

## 4. Death Star Sabotage targeting

Both sabotage validators (`FUN_0056a110` ordinary, `FUN_005744c0` DS) call `FUN_00593500` first. Its checks, in order: the base `FUN_00592600` (destroyed target `{0x40,0x21}`, en-route target `{0x40,0x22}`, container mismatch `{0x40,0x20}`, system-flag tests `{0x40,0x10/0x11/0x16}`), then family of the target object at mission `+0x38` in `[0x10,0x40)` else `{0x40,0x27}`, then **`+0x50` bit 2 (completed) set else `{0x40,0x34}`**. `FUN_005744c0` then demands family `[0x18,0x1c)` else `{0x40,0x29}`; `FUN_0056a110` refuses `[0x18,0x1c)` with `{0x40,0x28}` and characters with `{0x40,0x25}`.

So an uncompleted product cannot be targeted: it fails `{0x40,0x34}`.

**The Create Mission list for a system drop.** `FUN_005422f0` offers a record when `FUN_0054c590` accepts a temporary mission. That call first runs the record's target resolver (table `FUN_0054c720`; Sabotage and DS Sabotage both use `FUN_00592aa0`, stored at `0x0056a004` and `0x00574394`), which turns the order's target object into a location (an uncompleted object resolves through its producer's key `+0x38`, `FUN_00592aa0.c:41-53`), then the class validator (`FUN_0056a110`, `FUN_005744c0`). Both validators begin with `FUN_00593500`, which refuses a target whose family is outside `[0x10,0x40)` with `{0x40,0x27}`. A system drop names the system (family `0x90`), so neither Sabotage nor DS Sabotage is ever offered for a system target, whatever the system holds. VM, Alliance game, uncompleted Imperial Death Star at Coruscant, day 748: Han's list held Incite Uprising and Espionage only, as this predicts; the observation does not test the product. An object target (a completed ship, regiment or facility named from a window) reaches `{0x40,0x34}` when uncompleted.

**What `FUN_00507ab0` needs.** Its count walks the system's fleets and their `[0x18,0x1c)` children in mode 3 (section 2), so an unfinished Death Star counts through its container, the destination system's spare fleet, not the producer's system. The spare passes the mode-3 fleet filter from the order day (section 1). The mission's target slot (`+0x38`) holds the capital-ship object itself (not its fleet, not the facility); `+0x34` holds the location object. Success runs the target's slot `+0xac(6)` (`FUN_005746e0`, mission phase 3). Confidence: code read.

## 5. The AI's sabotage planners

The DS Sabotage planner (`0x6a000041`, constructor `FUN_00482020`, vtable `0x0065a958`) has slot `+0x48` `FUN_00482180` (team), `+0x4c` `FUN_00482330` (decoys), `+0x50` `FUN_00482560` (target). `FUN_00482180` builds a two-member team (`FUN_004035d0` queries, caps bit `0x80`, forbid `0x47400051`, combat and espionage 51) and `FUN_00482330` a decoy list capped at `FUN_004047d0` = 4; both are member selection, not target selection (`ai-mission-planning.md`).

**`FUN_00482560` (target).** It clears planner `+0x30` (target id) and `+0x34` (location). It then queries enemy fleet records that carry a Death Star: `FUN_0041a4c0(ctx, require 0x10, forbid 1, key 0x15, dir 2)` over the fleet records at `c+0x78` (record `+0x38` bit 0 = own fleet, bit `0x10` = a child ship class has flag `0x80`; `FUN_00433620`, `FUN_00433780`). It maps each to the fleet's system (record `+0x28`), and takes the first whose system record (context `+0x2c`, `FUN_00403d30`) satisfies `rec +0xbc / 2 <= team size (FUN_004bd000)` or `team size == planner +0x44()` (4). A system id in `0x90..0x97` goes to `FUN_00482910`, which requires the system record `+0x2c` bit `0x1000000` (set by `FUN_00433e40` only for the Alliance view: an enemy fleet with record bit `0x10` at a system), walks the system's usable fleets (mode 1, so a fleet needs a completed member), keeps a non-own fleet with bit `0x10`, and picks the first ship record in the fleet's list with class flag `0x80` (`ship +0x24`) as planner `+0x30`. The target is therefore a Death Star ship record in a usable enemy fleet. hyp: a fleet holding an unfinished Death Star next to a completed ship could be chosen, and the order's `{0x40,0x34}` would then refuse it.

**Who requests the mission.** The only writer of the DS Sabotage request is the strategy mission-priority table `FUN_004e8290`: only when the strategy side id (`this+4`) is 1, the running count `ctx+0x334 < 1` and `ctx +4` bit `0x4` is set (disassembly `0x004e8571`..`0x004e85ad`: `TEST AL,4`, `MOV [ESI],0x6a`); it drops the request when the bit is clear and the count is positive. `ctx +4` bit `0x4` is written only by `FUN_0041ba80`, from an **own** fleet record with bit `0x10` (own Death Star hull; the enemy branch of that function never touches it). The Alliance has no Death Star hull (record 136 is Empire-only), so the Alliance flag stays clear and the Empire never passes the side test: **the shipped AI never requests Death Star Sabotage.** Confidence: code read for each link, inference that no other writer exists (grep of the notes corpus for `| 4` on `+4` found one writer).

Ordinary Sabotage (`0x69`) has no entry in `FUN_004e8290`. It arrives as a regional recommendation: region record `+0xbc/+0xc0` set by posture slot 6 (`FUN_004b7150`, sector bit 8), taken by `FUN_004d2690` → `FUN_0042f640`. Its planner slots (`FUN_0047d520` team, `FUN_0047d720` decoys, target slot) are not read for target choice here.

## 6. The AI's Death Star build

`FUN_004ca5e0` (module 11, request) reaches the Death Star row only when no counted request exists: the six counts over `c+0xd8` records (`rec +0x64` bits `1`, `0x80`, `4`, `8`, `0x10`, `0x800`) are all zero or blocked, the troop-capacity row (`c+0x260 < c+0x20c`, blocker `0x4000000`) does not apply, and then all of: `m+0x30 == 2` (Empire), more than one system in the module's list (`FUN_005f50e0(m+0x78) > 1`), `c+4` bit `0x4` clear (no own Death Star fleet), blocker `0x20000000` clear. It sets mask `0x80`, key `0x200`, blocker `0x20000000` (no `0x100000`, so no ordinary capital-ship request matches it).

`FUN_004ca910` then clears every blocker, computes the budget `FUN_004cc220`, and `FUN_0041b270(ctx, 0x28, 0x80, 0x200, dir 1)` returns the side's available shipyard classes whose node `+0x18` has `0x80`: only record 136. It accepts the class only when node `+0x20` (maintenance, 600) is `<= budget`; otherwise it sets the blocker (skip next pass) and returns 0.

**The budget gate.** `budget = (30 * c+0x184 / 100) * 90 / 100 - c+0x24c`, forced to 0 when it exceeds `c+0x184 - c+0x188` (`c+0x184` = side capacity `+0x58`, `c+0x188` = `+0x5c`, setters `FUN_00418970`, `FUN_00418990`; `c+0x24c` = capital-ship maintenance already fielded, `FUN_0041ba80`). So 600 needs capacity of at least 2,223 plus 3.7 times the fleet's maintenance (46 mine and refinery pairs, none spent), and spare capacity of at least 600. Confidence: code read for the formula.

**In the port's playtest** (release build, dual AI, standard galaxy, medium difficulty, seeds 1-24, 2026-10-17): capacity is not what keeps the hull out. The Empire's capacity reaches 2,223 by day 1,500 in 17 seeds (median 2,725 at day 1,500) and holds 600 spare as well in 15. The subtracted term is: fielded capital-ship maintenance `c+0x24c` has median 636 at day 1,500 and 833 at day 3,000, so the budget's median is 35 at day 1,500, 15 at 3,000 and 13 at 5,000; module 11 spends its own 27% on ordinary capital ships. Of 240 samples (days 500 to 5,000 by 500) three admit 600 (seed 22 day 2,000: 730; seed 7 day 2,500: 640; seed 4 day 3,000: 607), and the class is listed in all 240. No seed builds the Death Star or issues 0x223 in 5,000 days. Around seed 22's day 2,000 the module builds CAPSHPSD `0x81` and `0x82` instead, so a row before the Death Star row holds those turns (hyp: the transport row `c+0x260 < c+0x20c` or a counted request; the playtest does not trace the row chosen).

If the budget did admit it, the order is a plain Build `0x211` at the producer system (`FUN_004cba90`, no Destination, quantity 1), which then meets §3 (spare 600) and §2 (no other `[0x18,0x1c)` ship at the system, own or enemy), then §1.

## 7. The production manager, its queue and the product key

Each system holds three production managers (family `0xa0`..`0xaf`, vtable `0x0065fbf8`), direct children that the system initializer creates completed (`FUN_0050e200.c:24-38`): `0xa2000006` (kind 0, ships and fighters), `0xa4000007` (kind 2, troops and special forces) and `0xa0000005` (kind 1, facilities). `FUN_00509670(system, k)` returns the first such child whose slot `+0x1ec` returns `k` (`FUN_00509670.c:18-24`): the producer of an area, not a queue position. The manager keeps its products' keys in the list at `+0x54 → +0x18` and the current product's key at `+0x74` (ProductKey, `build-delivery.md`). `FUN_0052aac0` chooses it: with `+0x58` nonzero it keeps the current product while `FUN_00528890` still accepts it, else walks the list in order and takes the first entry `FUN_00528890` accepts (created, none of completed, destroyed or en route, and `+0x38` equal to the manager's own id, `FUN_00528890.c:13-34`); with `+0x58` zero and an empty list it clears the key. An entry joins the list on the product's event `0x300`: `FUN_005140c0.c:66-77` → `FUN_00529cf0` → `FUN_0052a710`, which adds the key when `FUN_00528890` accepts the product and removes it when it does not, then reruns `FUN_0052a9c0`, `FUN_0052a7d0` and `FUN_0052aac0`. `FUN_00529cf0` then runs `FUN_00529dd0`, which matches the system's yards to the work left. A yard counts when its slot `+0x204` equals the manager's `+0x1ec` (kind), it is usable, and its side bits equal the manager's (`FUN_0052bde0`). With no such yard, `FUN_00529dd0` calls `FUN_0052a2c0` and every product of the manager is destroyed (`FUN_00529dd0.c:63-64`). Code read. A change of the system's holder destroys them too: the holder change's child walk (`FUN_004fae40`, slot `+0xb0` `FUN_004f8680.c:28-31`) gives each manager the new side (`FUN_004f6f40`; slot `+0x50` is `FUN_0051ebb0`, which accepts any side), and the manager's side hook (slot `+0xf0`, `FUN_0052b790.c:7-14`) runs `FUN_0052a2c0`, reason `0x16` for every listed product wherever it sits. A capital ship product of another system's manager sits in a fleet, which the walk leaves alone (`FUN_0051ebb0`), so it stays queued, unfinished and of its side, in a system the other side now holds (`facility-ownership.md`, "Control change").

The tactical station export (`FUN_0040b0e0.c:184-203`) reads `FUN_00509670(system, 0)`, takes `+0x74` of that manager (`FUN_0040d760`) and exports the product as an uncompleted station when its family is `[0x18,0x1c)` and its `+0x50` bit 2 is clear (`FUN_00506260`). The station is therefore the ship manager's current product alone: a Death Star queued behind another ship of the same area is not exported while that ship is current, and the troop and facility managers are never read. The product's hull is `+0x248` minus `+0x274` (`ship-damage-repair.md`); damage reaches a ship through the battle import and the repairs, which walk usable ships only (`tactical-death-star.md`, section 9), so an unbuilt product's `+0x274` is its initial value (inference: the object is created zeroed).

What a Destroy System does to these managers and their products is in `death-star-strategic.md`, "Missions, builds and arrivals at a destroyed system" ("Builds").

- **One Build, one fleet.** One Build of two Carrack cruisers at Coruscant puts both ships (`+0x50` `0x42`) in one new fleet (`0x10046`), and a fresh empty spare appears (§1).

A fleet holding only the unfinished ship greys Planetary Bombardment and Planetary Assault (`FUN_004ffa70`, `1`/`0x10`) and Scrap; the fleet Scrap's test is not traced.
- **Move.** Fleet 6, holding only the unfinished Death Star, moved from Coruscant to Averam within days and was never en route. The fleet is immobile (`FUN_004fda10`), so the mover check skips its speed test (`FUN_00555920.c:31-33`) and the execute reparents it at once (`FUN_00556390.c:12-14`).
- **Join.** A ship Move into another fleet, and a fleet-onto-fleet Join, both carry the unfinished ship with the rest: a Join reaches the ships one by one (`FUN_004ffc90.c:19-38`, mode 3). The emptied fleet disbands (state `0x14`). After the Join the ship's `+0x50` reads `0x142`: bit 8, `0x100`, is `GameObjObservedByEmpire` (`build-delivery.md`, "State bits used"). Its setter for a ship is not traced.
- **Destination.** The ships band's Destination released on Fleet 1 moves the queued Death Star into Fleet 1 (still `0x42`), disbands Fleet 6, and the band reads "Destination: Fleet 1". A Destination to Averam moves it into one fleet at Averam and keeps its progress. The facility icon's Destination released on Fleet 1 changes nothing and shows no advisor line (`production-destination.md`).
- **Build over a queued Death Star.** The ds-b line, day 151, Empire maintenance raised by 4000: the Coruscant ships band read "Death Star 1, Building: 1, Destination: Fleet 6", and Build → Death Star read 584/600, 2336 days, with Confirm live. Confirm was accepted with no refusal, and the band read "Death Star". In the next save `0x18000df5` is gone from every graph, a new `0x18000e4f` (`+0x50` `0x42`, manager `0xa200074f`) is the only ship of the same Fleet 6 `0x08000aea`, which did not disband, the manager's word 8 reads 1 (2 before), and free maintenance stays 4309 (§2, "What a Build gives back").
- **Stop.** It first asks "Are you sure you want to stop construction of the following? 1 Death Star" (TEXTSTRA 28755) over the advisor art, with a checkmark and an X. Then the ship's state byte is `0x16` and the fleet's `0x14`, and the band resets to "Destination: Coruscant".
