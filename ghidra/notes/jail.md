# Jail abodes: the trip, the finder row, entry, escape, targeting, the final battle

Confidence tags: **code read** (decompile or disassembly), **inference**, **needs VM** (the original running).
Companion: `death-star-strategic.md` ("Jail abodes", family `0x98`), `mission-lifecycle.md`, `build-delivery.md` ("Travel").

## 1. A captive's side is the captor's side

Every change of the prisoner bit (`+0xac` bit 0) runs the character hook at vtable slot `+0x34c` (`FUN_004ee800.c:22` -> `FUN_004f1a80`). The hook runs five steps, each only if the previous one reported a change (`FUN_004f1a80.c`):

1. `FUN_004eeb10(c, prisoner)` sets `+0xac` bit 8 to the new prisoner value (bit 8 arms the escape timer, section 5).
2. `FUN_004eeb80(c, 0)` clears `+0xac` bit 9 (the escaped bit).
3. `FUN_004eec60` sets the side bits `+0x24` 6-7 (`FUN_004f6f40`): for a prisoner, the opposite of the native side (native 1 gives 2, native 2 gives 1, native 0 gives 1); for a free character, the native side. The native side is `FUN_004edc80`: class record `+0x40`/`+0x44` (DAT is_alliance / is_empire): Alliance-only 1, Empire-only 2, otherwise 0 (`FUN_004edc80.c`). Code read.
4. `FUN_004eef90` sets `+0xac` bit 1 when the container's side equals the character's side and it is neither a prisoner nor destroyed.
5. `FUN_004ef070` (`+0xac` bit 7, the discoverer bit) and `FUN_004eeed0`.

So a prisoner carries the captor's side bits while held. This is why Rescue (MISSNSD `0x11`) reads only its opponent-side column (`+0x84` = 1; own-side and other-side columns 0), why the AI record counts "a character prisoner on the side that holds it" (`ai-mission-planning.md`), and why the jail abodes require occupants of their own owner side (`FUN_005775a0.c:57-65`, `(child +0x24 ^ abode +0x24) & 0xc0 == 0`): the Alliance Jail (`0x98000440`, owner 1) holds Empire characters, the Empire Jail (`0x98000480`, owner 2) Alliance characters. Code read.

## 2. The trip to a jail (question 1)

- **Abode slot `+0xc`** (vtable `0x00669260`, `FUN_00577130`) copies the abode's own key into the out parameter and returns 1; slot `+4` (`FUN_00577520`) returns the family `0x98`. It does not walk to a parent. `FUN_004f7d50` (the creator, `FUN_00519910`) builds the abode, sets its owner, then calls its slot `+0xa8` with the root's key: the abode's parent is the root object (the `+0xcc..+0xdc` fields), never a system. Code read.
- A character's slot `+0xc` is `FUN_004f6a80`: the parent's slot `+0xc`, recursively. For a character inside an abode it therefore returns the abode's key; for one in a system or fleet, the system's key. Code read.
- **Phase 4 of the hidden Autorouting mission** (`FUN_00524b70.c:79-128`): `FUN_00556430(member, +0x6c, +0x78)` then `FUN_00556390(member, +0x74)`. For `FUN_00547740` / `FUN_005475f0` / `FUN_00547480` the mission's `+0x6c` is the common origin of the group (`FUN_0054bf00`), `+0x70`/`+0x74` the destination key given by the caller (the jail key), and `+0x78` the destination object's slot `+0xc` output, which for an abode is the abode key (`FUN_00547ba0.c:135-140`: `FUN_00521a00`, `FUN_00521ab0`, `FUN_00521b60`, `FUN_00521c10`). Code read.
- `FUN_00556430` -> `FUN_00555d30` -> `FUN_00555b30`. The call is `FUN_00555b30(this, speed, view, from, to, &ticks)` with `view = (member +0x24 >> 4) & 3` (disassembly `0x00555d49`-`0x00555d75`; the speed slot `+0x34` consumes the pushed `1`). Both keys resolve through the registry at that view. `ticks` is zeroed (`FUN_00555b30.c:44`), then set to 1 whenever the two location keys differ (`FUN_00555b30.c:80-81`), then replaced by `FUN_0055d8c0` only when both location objects have a family in `0x90..0x97`. An abode has family `0x98`, so the test fails and `ticks` stays 1. Code read.
- Back in `FUN_00556430.c:42-55`: `FUN_004f7640(member, 1)` sets en route active (`+0x50` bit 5), `FUN_004f8010` arms timer `0x387` with delay 1, `FUN_004f7120` stores the destination key at `+0x3c`, `FUN_004f7870(member, 1)` sets autorouting (bit 11), `FUN_004f7390` stores `clock + 1` at `+0x44`. `FUN_00556390` then reparents the member into the abode at once (its branch that clears en route is skipped while bit 11 is set, `FUN_00556390.c:19`). Arrival is the `0x387` timer one tick later (`FUN_004f7fc0` clears bits 5, 11, 12; `timer-scheduler.md`).

**Answer.** The trip to a jail abode is 1 day, not 0 and not distance-based. The character sits in the abode's child list from phase 4 and is en route (bit 5, derived bit 4) until the `0x387` timer fires on day +1. Exceptions: the origin key equals the abode key (a member already in the jail): same keys, `FUN_00556430` returns success without a transit (0 days); a member with autorouting already set is not restarted (`FUN_00556430.c:25`). **Code read, high.** Needs VM: the displayed state during that day (the Personnel Finder jail branch shows no state, section 3).

## 3. The Personnel Finder row for a jail occupant (question 2)

`FUN_00465bb0` has no `unaff_EBX` ambiguity once read as assembly: the key tested at each family branch is the local at `[ESP+0x10]`, the output of the character's slot `+0xc` (`0x00465c07`). For a jailed character that key is the abode's. The branches (`0x00465cbb`-`0x00465d22`, `0x00465fed`):

- family `0x90..0x97` or `0x14..0x1b`: location text plus state words and rank (the system / fleet branch documented in `personnel-finder.md`);
- family `0x98..0x9f` (`0x00465fed`-`0x00466068`): `FUN_005f3c20` clears the location string, `FUN_004f62d0(this[7])` + `FUN_00583c40` append the container's name (`this[7]` is the abode), and the row is marked built (`+0x6c = 1`). Control jumps to `0x0046606f`; the state-word code (`0x8744`-`0x8747`) and the rank code (`0x8800`-`0x8802`) are never reached.

**Answer.** The row is `<character name> - <abode name>` (separator TEXTSTRA `0x1897`, assembly at `0x004660c4`), for example "<name> - Empire Jail". It carries no "Captured", no "Enroute", no "Injured", and no rank. The destroyed branch (`+0x50` bit 3) is tested before the family branches. **Code read, high.** The abode names are ABODESD names (TEXTSTRA 11600 Alliance Jail, 11616 Empire Jail). VM: "Leia Organa - Empire Jail" (Alliance game) beside "Luke Skywalker - Coruscant ( Captured )" for a captive held at a system, and "Emperor Palpatine - Alliance Jail" (Empire game).

## 4. The second way into jail: mission end (question 3)

`FUN_00546ea0` runs `FUN_00548120` after every phase change. For each member of the three lists (team `+0x84`, decoys `+0x8c`, captured `+0x94`; families `0x30..0x3f`) it asks `FUN_00521220(mission, member, &need, &route, &check)`:

- With no end code (`+0x64 == 0`) and the member's `+0x78` bits 2-3 clear, all three outputs are 0 and the member is skipped.
- `need` is always 1 otherwise. `route` is 1 when the member has autorouting set (`+0x50` bit 11), or the mission's return policy is 2, or the policy is 1 and the member's side differs from its container's side. `check` is `route` and policy != 2 (`FUN_00521220.c`).
- The policy is the MISSNSD record word `+0x68` (`FUN_00520ba0`, file column 10, `MissionRecord::return_policy`): **0** for Move, Return, Autorouting, Adrift; **1** for Diplomacy, Rescue, Sabotage, Espionage, Reconnaissance, Recruitment, Abduction, the three Research kinds, Incite Uprising, Death Star Sabotage, Jedi Training, Subdue Uprising, Assassination; **2** for Dagobah, Palace, Vacation, Sabbatical, Pickup, Bounty. Read from `data/base/MISSNSD.DAT` and TEXTSTRA 11265-11395.

`FUN_00548120` handles members with `route == 0` and `+0x78` bit 2 clear in place: mission slot `+0x1d0` (`FUN_00522fc0`) with flag 0 takes them off the mission and they stay where they are. `FUN_00548910` (looped until it reports no work) handles members with `route != 0`:

1. `FUN_00542ee0(member, mission, check, &dest)`. A mission key family outside `0x50..0x7f` (the hidden missions) goes straight to `FUN_00543040`. For `0x50..0x7f` with `check` set: if `FUN_00554170` accepts the member's current system (route table check, `FUN_005511d0` family), that system is the destination (the group stays put); else `FUN_005543c0` tries the character's stored `+0x70` key; if no destination results, `FUN_00543040(member, check, &dest)`. With `check` null (policy 2) it is `FUN_00543040` directly. Inference for the acceptance-table semantics (names only: the `FUN_00551xxx` family was not read); code read for the order.
2. Members with the same destination form a group (`FUN_00548910.c:85-126`); a destination of null counts as equal to another null.
3. A group with no member in the team or decoy list (only captives, `local_80 == 0`): `FUN_00549850` releases each non-destroyed prisoner (slot `+0x218`), no Return. A group with a team or decoy member and a destination: `FUN_005475f0` starts the hidden Return mission `0x42000002` (`FUN_00547ba0`, prisoner flag = the mission's `+0xa4` bit 2). A group with a team or decoy member and **no destination**: `FUN_00549580`, the jail path.

**Which members.** All of them, team, decoys and captives together, as one group per destination; the captive's destination is computed on its own (current, flipped) side, so a captive normally shares the team's destination only when both reach the same system. **Both sides:** the code names no side except through `FUN_00543040` (below) and the side bits used by `FUN_00549580`.

**When there is no destination.** `FUN_00543040` fails when `FUN_005431e0` (origin: the character's location when a system, else `+0x74` when a system (the system of the container the character joined its mission from, `+0x70`; `mission-return.md`), else Yavin `0x92000121` for side 1 or Coruscant `0x90000109` otherwise), `FUN_00543360`, or the retreat chain `FUN_005545e0` (passes `FUN_00554740`, `FUN_00554ab0`, nearness `FUN_00554e80`, each accepting only systems of the character's own side that pass `FUN_005571c0`) yields no system; a Bounty member (mission family `0x65`) never fails: `FUN_00543040.c` returns Jabba's Palace `0x98000481`. In practice the chain fails when no system on the character's current side accepts it. Inference.

**What a system must pass to accept a returning character** (candidate test `FUN_005571c0`: route kind `0x241` for families `0x30..0x3f`, built by `FUN_005511d0` with the character's own side bits as both side fields (`FUN_00551100.c:14-15`), then the move placers `FUN_00551630`; the system's check is `FUN_005073d0` -> `FUN_00553410`). Code read:
- side: the system's side bits equal the character's, else refusal `1/0x24` (`FUN_00553410.c:22-30`; both side arguments are the character's side);
- not destroyed (`+0x50` bit 3, `0x22`), completed (bit 2, `0x20`) and not en route (bit 4, `0x21`);
- blockade (`+0x88` bit `0x20`) is lifted for the character kind (`FUN_005073d0.c`, `0x90/4` raised then waived when the object is a family `0x30..0x40` character); it only reorders the chain (stage 3 skips blockaded systems, stage 5 takes them);
- room is unlimited for characters; no test reads population, popularity or unrest in this path. Inference for the plumbing from `FUN_00551100` to the two side fields; the `FUN_00552300` / `FUN_00552dd0` legs were not read.

So stages 6 (neutral systems, side bits 3) and 7 (other side) of `FUN_005545e0` offer candidates that fail the side test; only a system of the character's own side, completed, intact and idle, accepts. Inference from the same plumbing.

**Why the jail is nearly unreachable.** `FUN_00549580` flips the side first (section 4, step 1) and reruns `FUN_00543040` for the captor's side. Stage 1 offers the character's current container and its parents, so a team ended at an enemy system is already inside a system of its new side and goes there, as a captive. The jail needs both sides to fail: no accepting own-side system (including `+0x70`), no accepting captor-side system, and a container that is destroyed or not of the captor's side. In a Standard game that means no intact, completed system on either side, a state the game probably ends on first (inference; no victory read for it). Needs VM; none of the library saves can be edited to it with a few bytes (every system owner word, in three graph copies, or every state word).

**What `FUN_00549580` does, per member** (existing member, not destroyed):
1. Free member: slot `+0x20c` (capture, status 0). The hook of section 1 flips its side to the captor's. Prisoner member: slot `+0x218` (status 2, prisoner bit clear, native side restored).
2. `FUN_00543040(member, 0, &dest)` runs again on the member's side **after** step 1.
3. Only if that again gives no destination: a member that is free again (the released prisoner) is captured again (slot `+0x20c`, `FUN_00549580.c:78-93`), and the jail is chosen from its **current** side bits (`+0x24` & 0xc0 == 0x40: `0x98000440`, else `0x98000480`).
4. `FUN_00547740` starts the hidden Autorouting to `dest` with the prisoner flag read after step 1/3.

A special force (families `0x3c`..`0x3f`) in the group never reaches steps 3 and 4: its prisoner slot `+0x1d4` is `FUN_006158b0` (0), so step 1 takes the free branch, and its capture slot `+0x20c` is `FUN_00503eb0` (special-force vtable `0x0065e160`), which calls `FUN_00524fb0` (returns 1) and then `+0xac(9)`: the special force is destroyed with reason 9 (`FUN_00549580.c:56-60`). The jail never holds one. Code read; the text and effects of reason 9 are not traced.

So a stranded free team member is captured first and is sent to a system of the opposite side if that side's retreat chain accepts it; only when that chain also fails does it reach a jail, and the jail is the captor's (opposite side's). A prisoner in the group is released, tries its native side, and returns to its captor's jail when nothing accepts it. Code read for the order and the flip; inference for "opposite side" systems accepting a captive (not seen in a trace). Needs VM: a campaign state in which a team's side has no accepting system.

## 5. Escape (question 4)

- **What arms it.** Bit 8 mirrors the prisoner bit (section 1, step 1). `FUN_004eeb10` calls slot `+0x368` (`FUN_004f1ba0`): `FUN_0053fa60(0x38a, bit, char, charBlock+0x28)`, arming timer `0x38a` on the character. The delay record is written by `FUN_004ef750.c:16-17` from GNPRTB `0xa18` (2584) and `0xa19` (2585): minimum 100 days plus a uniform draw of 0-1000 days (shipped, all eight columns), repeating while the record is unchanged (`timer-scheduler.md`, "Firing"). Code read; the GNPRTB loads are `FUN_0053e450.c:171-178`.
- **What fires.** The timer's fire slot `+0x30` is `FUN_0057d330` -> `FUN_004ef150`: if bit 8 is still set, `FUN_004eebf0(c, 1)` sets `+0xac` bit 10, then `FUN_004eebf0(c, 0)` clears it. Each change calls slot `+0x370` (`FUN_004f1be0`), which posts event `0x317` with the new bit value (`FUN_0053f9c0`). Event `0x317`'s class (vtable `0x006699a8`, id slot `+0x24` = `FUN_0057d510`, fire slot `+0x20`) is `FUN_0057d670`: it resolves the target character and calls `FUN_00561990(char, value, ctx)`; the value-0 post does nothing (`FUN_00561990.c:21`).
- **The roll** (`FUN_00561990`). The container is `FUN_004f6b50`. With bit 8 set and a container, it iterates (`FUN_004f2640`: families `0x30..0x3b`, direct children, side = the character's current side, i.e. the captor's side) the non-prisoner characters (`slot +0x1d4 == 0`) and averages their combat (`slot +0x1f0`, short `+0x86`), and counts same-side regiments (`FUN_00504cc0`, `0x10..0x13`). `x = espionage (+0x1e0, short +0x7e) + combat (+0x1f0) - averageGuardCombat - regimentCount`; `FUN_0055e7e0` looks `x` up in ESCAPETB (id `0x2c`; `FUN_0053e340` -> `FUN_0055bed0` -> `FUN_0058b7e0`, `FUN_00595090`: the last row whose threshold is at most `x`, the first row when `x` is below all). Shipped rows (threshold: percent): -50: 1, -49: 2, -31: 3, -11: 5, 10: 10, 20: 15, 30: 20, 40: 25, 50: 30. A uniform draw 0-99 below the percent succeeds (`FUN_0053e2f0`).
- **Success.** `FUN_004eeb80(c, 1)` sets bit 9; slot `+0x36c` (`FUN_004f1bd0`) -> `FUN_004ef0c0`: if the prisoner bit, `+0x50` bit 0 and bit 9 are set and `+0x78` bit 7 (on a mission) is clear, slot `+0x214` (`FUN_004ef570`) writes status 1 (free). The status hook clears the prisoner bit, restores the native side (section 1), clears the captor key (`FUN_004ef190`) and requests autoscrap (`FUN_004f78e0(1)`, `FUN_004f18e0`).
- **Can a jail occupant escape?** Yes. A jail occupant has the prisoner bit, bit 8, and a container (the abode), and the abode's child list holds only characters, so the guard average is 0 (no free same-side characters unless an earlier escapee remains) and the regiment count 0: `x = espionage + combat`, a 1-30 percent chance per fire (about 10-30 for typical officers), a fire every 100-1100 days. **Where to:** nothing in the escape path chooses a destination. The character is free, native side, inside an abode of the other side, and flagged; the adrift sweep (`FUN_00549230` -> `FUN_0054c7d0.c:55-155`) groups flagged characters whose container is destroyed or of another side, sends the group to `FUN_00543040` (origin: Yavin for side 1, Coruscant otherwise, because the location is an abode; then the retreat chain on the native side) and starts Autorouting/Adrift. The trigger is traced. The flag raises event `0x307` (queued, priority `0x300`; `death-star-strategic.md`, "Autoscrap request"), whose handler `FUN_00515480` takes a completed character to `FUN_00545df0` → `FUN_00548da0`. That function proceeds when the character holds `+0x50` bit 12 or `+0x78` bit 6 (`FUN_00548da0.c:22`), asks the character's location (slot `+0xc`: the abode key) and sweeps it with `FUN_00548e90`. `FUN_00548e90` gathers only characters with the adrift bit (none for an escapee, which holds the request bit alone), then dispatches `FUN_00549230` on the location unless it is a system `0x90..0x97` holding the battle bit (`FUN_00548e90.c:122-141`), so an abode is dispatched. `FUN_00549230` → `FUN_0054c7d0` scans the abode's direct character children (`FUN_00536da0`, mode 3), takes each flagged one with no captor key (the escape cleared it) whose container is of another side (`+0x24` bits 6-7 of the abode against the character's native side: the jail holds the other side's characters, section 1) and groups it by `FUN_00543040` (`FUN_0054c7d0.c:84-120`; the flag clears at `:146-155`). `FUN_005431e0` finds no system for the abode key (family `0x98`) and reads the character's `+0x74`, which is null off a mission (the OnMission clear nulls `+0x70`, `mission-return.md`, section 3); it then answers Yavin for side bits 1 and Coruscant otherwise, so an Empire escapee from the Alliance Jail starts from Coruscant by the same code. The retreat chain then runs on the native side from that origin. Code read for the chain, VM for the Alliance case. VM (`alliance-day731-leia-jailed.sav`, Leia in the Empire Jail): within about 50 days "Leia Organa Escaped" files ("Leia Organa escaped from the Empire at Empire Jail.", the escape picture), then "Leia Organa Arrives at Yavin" ("I have arrived at Yavin."), and the finder reads "Leia Organa - Yavin": the destination is Yavin, as the origin rule gives for side 1.

## 6. Rescue targeting (question 5)

- **Mission legality, target in a family `0x98` container.** `FUN_00542b60` checks only the order's family (`0x240` needs `0x50..0x7f`, `.c:36-70`). The creation-only container check accepts families `0x90..0x97` and `0x98..0x9f` together (`FUN_00592600.c:35-72`, status `0x40`/`0x10` otherwise), so an abode container is legal. Abode slot `+0x74` (`FUN_00577270`) passes order `0x240` for children `0x30..0x3f` into `FUN_00553410`. The running checks (`mission-lifecycle.md`, "The running checks") read the target's side: for Rescue the opponent column only, so a jailed captive is a legal Rescue target for its native side (its current side is the captor's) and illegal for the captor. Its prisoner column (`+0x90`) is 1. `FUN_00586c80` and `FUN_00586e20` read no location: families `0x30..0x3b` only.
- **Player.** Targeting is a click on the object a child window returns from its vtable slot `+0x68` (`object-popup-menu.md`, "Targeting"). The Personnel Finder (type `0x17`, vtable `0x0065a130`) returns the null key from that slot (`FUN_004ac4b0.c`: `FUN_004ece30` and a copy). No system list contains a jailed character (its parent is the abode). So the player has no click path to a jail occupant. Code read for the finder; inference for "no other window shows it".
- **AI.** `FUN_0047e270` is the Rescue planner's **team** selector (`FUN_004035d0` over the planner's own-side character records: required `0x2`, capability `0x2`, forbidden `0x4f400051` which includes the prisoner state `0x40`, combat 51-10000), and `FUN_0047e3f0` the decoy selector. Neither picks a target. The planner's target is stored at planner `+0x30`/`+0x34`/`+0x38` before state 6; state 6 (`FUN_004bd0a0.c:40-200`) accepts a location only of family `0x90..0x97` and walks a member's parent chain until it finds one; an abode's parent is the root, so a jailed target never yields a system. What constructs a Rescue planner with a target (the side `+0x318`/`+0x31c` choice) was not traced. Inference: the AI cannot reach a jail occupant; needs VM or a trace of the planner construction.

## 7. The final battle (question 6)

`FUN_0054b040` is a duel of three characters in one container: Luke (`FUN_00507010`), Vader (`FUN_00507070`), the Emperor (`FUN_00543800`), found with their containers (`FUN_005434b0`, `FUN_00543760`, `FUN_00543800`) and required to share one container key. It does not name an abode (no `0x98` constant, no `FUN_00549580`). Luke's Force (`+0x8c`) against GNPRTB `0x1807`:

- Below: result 2. Luke's bit 8 cleared (`FUN_004eeb10`), Luke injured (`FUN_00549a20`, slot `+0x2f0`, cause 10).
- At or above: result 1. Luke slot `+0x218`, Vader and the Emperor slot `+0x20c` (captured), bit 8 cleared on both.

Then, when the winner's container is of the other side (`FUN_0054b040.c:263-270`: result 1 compares Luke's container with Luke, result 2 compares Vader's container with Vader), it builds a list of **all three** characters and a destination `FUN_00543040(winner)` (result 1: Luke, result 2: Vader), and starts `FUN_00547480(side = result, dest, list)`: the Move mission `0x41000001` (`FUN_00547ba0`, prisoner flag 1). With no destination no Move is issued and nobody moves (no jail fallback). **Confirmed: the losers go by Move to the winner's `FUN_00543040` destination, never to a jail abode.** Which register holds the captor key passed to slot `+0x20c` is not resolved (the decompile mixes `unaff_EBP`, `unaff_ESI`, `unaff_retaddr`); a Luke defeat branch calls no capture. Code read for the Move and the absence of an abode; inference for the captor key.
